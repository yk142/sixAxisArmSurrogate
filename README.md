# sixAxisArmSurrogate

6軸垂直多関節ロボットアーム(肘型+球状手首)の物理モデルをNeural State Space (NSS)
モデルでサロゲート化するプロジェクト。

姉妹プロジェクト [scaraSurrogate](https://github.com/yk142/scaraSurrogate)
(2-3軸のスカラ/空間マニピュレータ)・[surrogateRolloutVerification](https://github.com/yk142/surrogateRolloutVerification)
(振り子)で得た教訓を踏まえて進める。特に「既知の物理構造(質量行列・コリオリ・重力項)を
ハードコードし、NNは摩擦の係数のみを学習するグレーボックス化」が効くことが分かっている
ため、本プロジェクトでもこの知見を最初から適用する。

## 対象系

EPSON C8A901S(6軸垂直多関節ロボット、肘型+球状手首)の**軸の向きだけ**を参考にした
標準的な6軸マニピュレータ。細かい寸法・質量・慣性は実機と一致させておらず、妥当な範囲で
任意に設定している。

```
i | a_i | alpha_i | d_i  | theta_i
1 | 0   | 90°     | 0.3  | q1 (腰・ヨー)
2 | 0.5 | 0       | 0    | q2 (肩)
3 | 0.5 | 0       | 0    | q3 (肘)
4 | 0   | 90°     | 0.5  | q4 (前腕ロール)
5 | 0   | -90°    | 0    | q5 (手首ピッチ)
6 | 0   | 0       | 0.1  | q6 (手首ロール)
```

q1-q3はscaraSurrogate Phase3(ヨー+肩・肘)と同じ軸構成。q4-q6が球状手首(3軸の回転軸が
1点で交わる)を構成するため、scaraSurrogateで使えたブロック対角の簡略化は使えず、一般的な
空間剛体力学(DHパラメータ+再帰的ニュートン・オイラー法, RNEA)で運動方程式を構築する。

## 力学モデル

DHパラメータ表は**修正DH規約(Craig)**で解釈する(`src/physics.py`参照)。標準DH規約
(回転が先・並進が後)だとRNEAの再帰式が前提とする「並進オフセットは前段フレームの
剛体に固定されている」という条件が崩れることをM1実装時に発見したため(下記「教訓」参照)。

再帰的ニュートン・オイラー法(RNEA)で:
- 質量行列 `M(q)`: RNEAを単位角加速度ごとに(6回相当、実装は1回のバッチ呼び出しに
  まとめて高速化)呼び出す合成剛体法
- バイアス力 `bias(q,q̇) = C(q,q̇)q̇ + G(q)`: RNEAを1回(q̈=0)呼び出す

フォワードダイナミクス:
```
M(q) q̈ = tau - bias(q,q̇) - friction(q̇)
```
摩擦は粘性+クーロン(Stribeck風の滑らかな近似)。手首リンク(4-6)は腕リンク(1-3)より
慣性が1-2桁小さいため、摩擦係数も慣性スケールに応じて小さくしている(coulomb/viscous比
0.4は全関節共通)。

## サロゲートモデル(グレーボックス、構造化摩擦)

`src/model.py`にRNEAのtorch版(`src/physics.py`のnumpy実装と全く同じ式)を実装し、
質量行列・バイアス力を「既知の物理」として扱う。学習対象は摩擦係数のみ(関節ごとに
粘性・クーロン各1個、計12個)。姉妹プロジェクトで確立した「摩擦は自由形のMLPではなく
構造化モデル(関数形固定、係数のみ学習)」「損失は成分ごとに標準偏差で正規化」の教訓を
最初から適用する。

## マイルストーン

- **M1** (#1, #2): DHパラメータ+RNEAによる真値シミュレータ。エネルギー保存則を
  2秒間で相対誤差2.5e-5まで検証。
- **M2** (#3, #6, #8): ランダムトルク駆動のデータセット生成、グレーボックスサロゲートの
  学習、計算トルク法PTP制御での真値/サロゲート比較。摩擦係数(粘性/クーロン)の識別
  精度を上げるため、(a) データの一部(25%)を重力補償+小摂動トルクで駆動し低速域
  (V_STRIBECK付近)を探索するようにし、(b) 学習率をコサイン減衰(1e-2→1e-4)に
  切り替えた。最終的に摩擦係数はほぼ真値まで収束し(手首関節も含む)、計算トルク法
  PTP制御は2/2 IC成功(最終追従誤差0.056-0.065rad、真値モデルとほぼ同水準、
  しきい値0.2rad)。
- **M2追加検証**(#12): 始点・目標点をともに全域(-pi,pi)からランダムサンプリング
  した50シナリオで、任意の姿勢から任意の姿勢へのPTP制御を検証した。6秒間では
  真値モデルでも24/50しか収束しなかったが、これは発散ではなく単に大きな角度変化に
  対して収束が遅いだけと判明したため12秒に延長し、46/50(グレーボックスは41/50)が
  成功した。グレーボックスの誤差は真値モデルとほぼ同じ挙動(失敗ケースも含めて)を
  示しており、サロゲート自体の精度は妥当であることを確認した。過渡応答を可視化した
  ところ、失敗ケースの一部は単なる収束の遅さではなく、大きな初期誤差に対して関節が
  目標周辺に落ち着くまでに何周も巻き付いてしまい、真値とサロゲートで巻き付き回数
  (=最終的な絶対角度)が異なってしまう現象であることが分かった(下記「教訓」参照)。
- **計算速度ベンチマーク**(#14): グレーボックスサロゲートは真値シミュレータと
  同じRNEA計算をtorchで再実装しているため、計算速度はほぼ変わらない(単一軌道
  500ステップ・バッチ50本×200ステップのいずれも0.93倍、むしろわずかに遅い)。
  参考として純粋なMLP(NSSModel、ブラックボックス)は同条件で約96倍高速だった。
- **高速化(本題)**(#16): サロゲート化の本来の目的は高速化であるため、
  `torch.compile`でRNEAのPythonループのオーバーヘッドを削減した(再学習不要、
  物理構造・学習済み摩擦係数は完全に同一)。初回コンパイルには約30秒かかるが、
  以降は定常状態で真値シミュレータの2.5倍高速(バッチ50本×200ステップで
  7.68秒→3.09秒)。多数回のロールアウトが必要な用途(RL学習、MPC等)では
  コンパイルコストを償却できるため有効な選択肢になる。詳細は下記「教訓」参照。
- **高速化・バッチサイズの検証**(#18): バッチサイズを50→200→500と増やすと
  1軌道あたりのコストは大きく下がる(真値88.5ms→30.5ms→15.2ms、コンパイル版
  32.7ms→11.1ms→5.5ms)が、真値に対する倍率は2.70x→2.75x→2.77xとほぼ頭打ち。
  現在の設計(RNEAをそのまま使うグレーボックス)での速度向上の上限はおよそ
  2.7-2.8倍と考えられる。これを超えるには質量行列・バイアス力自体を軽量な
  NNで近似する必要がある(#19で検討)。
- **高速化(軽量NN、実験的)**(#19): RNEAの反復計算自体をなくすため質量行列
  M(q)・バイアス力bias(q,q_dot)を小さなMLPで直接近似する`LightweightGrayBoxModel`
  を試作した。速度はtorch.compileなしで真値シミュレータの約12-13倍だが、
  M2と同じ学習レシピでは精度が大きく劣化する(開ループRMSE 0.4-0.9→4.6-6.3、
  PTP制御失敗)ことを確認した。追加のデータ・学習時間なしでは実用に耐えない
  ため、現時点ではM2のグレーボックス(RNEA版)を正式な成果物とする。
- **実時間比の測定**(#22): 正式版(torch.compile込み)が実際の物理現象
  (dt=0.002s)に対して何倍の計算時間がかかるかを測定した。単一軌道(1台の
  ロボットをリアルタイム制御する想定)では実時間の約0.18倍(≒実時間の約5.4倍
  の計算時間、リアルタイムより遅い)。バッチ処理(50シナリオ並列)では1軌道
  あたり換算で実時間の約6.5倍(実時間より速い)。詳細は下記「教訓」参照。
- **高速化(numba、単一軌道)**(#26): 摩擦なしの参照物理(M(q)・bias(q,q̇))は
  学習パラメータを持たないため、推論・制御時はPyTorch外でも計算できることに
  着目し、`src/physics_numba.py`にRNEA・質量行列・バイアス力・計算トルク法
  PTP閉ループ全体をnumbaでJITコンパイルした実装を追加した。単一軌道では
  numpyの約45倍・torch.compile単一軌道版(#22)の約17倍高速で、実時間比は
  約3.2倍(プラント単体)・約1.8倍(コントローラ込みの閉ループ全体、真値
  モデルと数値誤差の範囲で一致)。単一軌道のリアルタイム制御という、
  torch.compileでは実時間に届かなかった用途(#22)を解決した。ただしバッチ
  処理には効果がない(各軌道が独立にJIT実行されるため)。#12と同じ50
  ランダムシナリオ検証をnumba版(Pythonループで逐次実行)でも行い、真値
  46/50・グレーボックス41/50・平均誤差もtorch版とほぼ完全に一致すること
  (数値的な等価性)を確認した。
- **軽量NNの精度改善(直接教師あり事前学習+段階的カリキュラム、#32)**:
  #19の軽量NNは#24(容量増)・#30(データ4倍)のいずれでも精度が伸びず、
  M(q)・bias(q,q̇)・摩擦を同時にロールアウト損失だけで学習する設計自体を
  疑い、2段階に分けて検証した。(1)ロールアウトを介さず、真の
  `mass_matrix(q)`/`bias_forces(q,q̇)`への直接教師あり回帰でmass_net/
  bias_netを事前学習した。M(q)は正規化なしの生MSEで相対誤差2.4%まで
  収束したが、bias(q,q̇)は当初生MSEで17.5%で頭打ちになった。関節ごとに
  内訳を見ると腕関節(q1-3)は12-23%だが手首関節(q4-6)はほぼ0%(ゼロ予測と
  同水準)で、腕関節の振幅(平均6.6-13.3)が手首関節(平均0.02-1.0)の
  1-600倍あるため生MSEでは手首関節の勾配がほぼ消えていたと判明した
  (Phase2-M8の教訓と同じ現象)。成分ごとの標準偏差で正規化したMSEに
  切り替えたところ、手首関節は改善したが(q6: 100%→63%相対誤差)、
  逆に元々良かったq1が悪化する(23%→76%)トレードオフが生じた(全成分を
  均等に扱うため、隠れ層を共有する小さなMLPでは全成分を同時に高精度化
  できない)。なおM(q)自体は成分間スケール差が軽微なため標準偏差正規化は
  不要で、逆に分散が極端に小さい成分(ほぼ定数)で正規化が数値不安定を
  招くことを確認し、M(q)は生MSEのまま維持した。(2)この
  mass_net/bias_net(正規化版)を凍結し、`StructuredFrictionGrayBoxModel`
  と同様に摩擦係数(12スカラー)だけをロールアウト損失で学習した。学習損失は
  0.0098までRNEA版(0.0016)に近づき(#30の0.0185より改善)、開ループRMSE
  (0.2秒、random torque)も5.22→3.34まで改善した。計算トルク法PTP制御
  (6秒)の最終誤差は0.36-0.38(#30は4.96-5.83)まで改善し、12秒に延長
  すると2件中1件成功(0.18)した。過渡応答では#19/#30で見られたq6の
  巻き付き・暴走(-2.2rad)が解消し1-2秒で収束するようになったが、代わりに
  bias_net正規化で相対的に悪化したq5が新たな律速要因になった(緩やかに
  目標から外れて戻る挙動)。M(q)は直接教師ありなら高精度に学習できる一方、
  bias(q,q̇)(コリオリ項・重力項)は関節間の振幅差が大きく、単一の小さな
  MLPで全関節を同時に高精度化するのは本質的に難しいことが分かった。

## 教訓

1. **標準DH規約とRNEAの再帰式のコンベンション不整合**: 標準DH規約(`Rot_z(theta)*
   Trans_z(d)*Trans_x(a)*Rot_x(alpha)`、回転が先)では並進オフセット`a`が関節自身の
   `theta`回転の影響を受けて回転してしまう。RNEAの標準的な再帰式は「並進オフセットは
   前段フレームの剛体に固定されている(現在の関節自身の回転に依存しない)」ことを前提に
   しているため、標準DH規約のままRNEAを書くと質量行列の非対角成分が関節角度に依存しない
   という物理的に誤った結果になる。2関節平面アームへの縮約検証(既知の解析解と比較)で
   発見した。修正DH規約(Craig: `Rot_x(alpha)*Trans_x(a)*Rot_z(theta)*Trans_z(d)`、
   並進が先)に切り替えることで解決する。

2. **関節ごとに慣性スケールが大きく異なる系では、トルク上限・摩擦係数・制御ゲインを
   関節ごとに調整する必要がある**: scaraSurrogateまでの2-3軸アームはリンクの慣性が
   同程度だったため全関節共通の定数で問題なかったが、本プロジェクトの球状手首(慣性が
   腕リンクの1/100程度)では、(a) 全関節一律のトルク範囲でデータ生成するとRK4が
   数値的に不安定化する、(b) 全関節共通の摩擦係数だと手首がクーロン摩擦に支配されて
   わずかな制御トルクでは動かせなくなる、(c) 全関節共通の制御ゲインだと腕関節側の
   トルクが飽和して減結合(計算トルク法の前提)が崩れる、という3つの問題が起きることを
   確認した。関節ごとの慣性スケールに応じてこれらを個別に設定する必要がある。

3. **RNEAをN_JOINTS回ループで呼ぶ実装は学習・制御のホットパスで大きなボトルネックになる**:
   質量行列M(q)はRNEAを単位角加速度ごとにN_JOINTS回呼ぶ合成剛体法で計算できるが、
   Pythonループで直列に呼ぶと(1回のdynamics呼び出しで7回のRNEA呼び出しになり)学習の
   多段ロールアウト損失や制御ループで大きなオーバーヘッドになる。RNEAが元々バッチ次元
   (`...`)に対応していることを利用し、N_JOINTS本の単位ベクトルを1つのバッチ次元に
   詰め込んでRNEAを1回だけ呼ぶことで、質量行列の計算をN_JOINTS倍高速化できる
   (numpy版・torch版の両方に適用、約5-6倍の高速化を確認)。同様にデータセット生成も
   軌道ごとに逐次シミュレートするのではなく、バッチ次元にまとめて`simulate_batch`で
   一括シミュレートすることで大幅に高速化できる。

4. **摩擦係数(粘性/クーロン)の学習には、識別可能性(データ)と最適化(学習率)の
   両方の問題があり得るため、切り分けて診断する必要がある**(#6, #8):

   - **識別可能性の問題**: ランダムトルクだけで駆動すると(特に重力補償なしの腕関節は)
     ほとんどの時間が高速域(`|q_dot| >> V_STRIBECK`)になり、`tanh(q_dot/V_STRIBECK)`
     がほぼ常に±1に飽和してクーロン摩擦が実質的に定数バイアスになってしまう。この状態
     では粘性・クーロンの寄与が観測上区別しにくい。データの一部(25%)を初期姿勢の
     重力補償トルク+小摂動で駆動し、V_STRIBECK付近の低速域に留まる軌道を混ぜることで
     改善する(#6)。
   - **最適化の問題**: 上記の対策後も摩擦係数(特に手首関節)は真値から遠かった。
     「学習損失を最小にする摩擦係数(真値)を手動で設定すると学習損失がほぼ0になる」
     ことを確認し、識別性ではなく最適化(学習率)の問題だと切り分けた。全パラメータが
     `exp(0)=1.0`から始まるのに対し手首関節の真値は0.01-0.05と初期値から2桁近く離れて
     おり、LR=1e-3固定では105エポックでもそこまで動き切らなかった。LR=0.05固定に
     上げると序盤は急速に改善するが最適点付近で減衰がなく発振・オーバーシュートする。
     コサイン減衰(1e-2→1e-4)で高LRから徐々に下げることで、序盤の速い収束と終盤の
     安定した微調整を両立した(#8)。

   両対策後、摩擦係数はほぼ真値まで収束し(学習損失0.034→0.0014)、開ループRMSEも
   大幅に改善(0.2秒間で最大3.3→0.86-0.96)、PTP制御の追従誤差も真値モデルとほぼ
   同水準(0.056-0.065rad)まで改善した。

5. **少数の固定シナリオでのPTP検証だけでは「収束が遅いだけ」の問題を見落とす**:
   固定した目標姿勢1つ+小さいオフセット4通りでは全て収束していたが、始点・目標点を
   ともに全域からランダムサンプリングした50シナリオで検証したところ、6秒間では
   真値モデル(サロゲートではなく)でも24/50しか成功しなかった。個別に追跡したところ
   発散ではなく、大きな角度変化(複数関節が同時に1rad以上ずれる等)に対して現在の
   ゲインでは単に収束が遅いだけだと判明した。シミュレーション時間を12秒に延ばすと
   46/50まで改善した。少数の「小さな摂動」シナリオだけの検証は、実用範囲の狭い
   部分しかカバーしないため、実際に使う範囲(ここでは「任意の姿勢から任意の姿勢へ」)
   に即した多数のランダムシナリオでの検証が重要(#12)。

6. **大きな初期誤差に対する計算トルク法PTPは、関節が目標周辺に落ち着くまでに
   何周も巻き付くことがあり、真値とサロゲートで巻き付き回数が食い違うと絶対角度が
   大きく異なる「疑似的な失敗」が起こりうる**: `angular_error`はラップした
   (-pi,pi]の誤差を使うため、コントローラ自身は「あと何回転したか」を意識しない。
   大きな初期誤差(例えば複数関節が同時に2rad以上ずれる)では、収束の過程で
   関節が目標を通り過ぎて巻き付くことがあり、真値モデルとサロゲートのわずかな
   力学の違いにより巻き付き回数(=最終的な絶対角度、2πの整数倍だけ目標からずれた
   別の不動点)が食い違うことがある(#12の最悪ケースで確認)。この場合、ラップした
   誤差で見ると大きな失敗に見えるが、実際には「制御自体が発散した」のではなく
   「どちらも収束はしたが、収束先が2π×整数だけ異なる」という質的に別の現象である。
   実運用ではこの手の大角度移動は経由点を刻む、あるいは巻き付きを許容しない多回転
   制限を入れるなどの対策が必要になる。

7. **「グレーボックス化=NNで置き換えて高速化」ではない。既知の物理をそのまま
   使う設計では計算速度の向上は原理的に期待できない**(#14): 本プロジェクトの
   グレーボックスモデル(`src/model.py`)は質量行列・バイアス力を「既知の物理」
   として扱い、RNEA(6リンク分のPythonループを含む前進・後退再帰)をtorchで
   そのまま再実装している。これは真値シミュレータ(numpy)と本質的に同じ計算量の
   計算グラフであり、実測でも単一軌道・バッチ軌道のいずれも速度差はほぼない
   (0.93倍、むしろ学習パラメータのオーバーヘッド分わずかに遅い)。一方、参考に
   測定した純粋なMLP(ブラックボックス、`NSSModel`)は同条件で約96倍高速だった。
   「学習済みサロゲートは常に元のシミュレータより速い」という思い込みは、
   グレーボックス設計(既知の物理構造をそのまま持つ)には当てはまらない
   (計算グラフの構造自体を変えない限り、原理的に速くならない)。

8. **サロゲート化の目的が高速化なら、物理構造・学習済みパラメータを変えずに
   `torch.compile`でPythonループのオーバーヘッドだけを削減する選択肢がある**
   (#16): #14でグレーボックスがほぼ高速化していないと判明したが、これは
   「アーキテクチャ(RNEAの反復計算)を変えなければ速くならない」という意味で、
   「torchで書き直しても速くならない」という意味ではない。`model.step`を
   `torch.compile`でラップしたところ、初回呼び出し(形状ごとに再コンパイルが
   必要、約30秒)の後は定常状態で真値シミュレータ(numpy)の2.5倍高速になった
   (バッチ50本×200ステップで7.68秒→3.09秒、出力は数値誤差の範囲で非コンパイル版
   と一致)。再学習は不要で、精度も変わらない。コンパイルのオーバーヘッドは
   1回だけなので、同じ形状で多数回ロールアウトする用途(強化学習・MPCなど)で
   有効な、副作用の少ない高速化手段。

9. **バッチ化とtorch.compileは同じ種類の高速化(固定オーバーヘッドの償却)を
   別の軸で行うため、両者の効果は掛け算にならず頭打ちがある**(#18): バッチ
   サイズを50→500に増やすと1軌道あたりのコストは真値・コンパイル版ともに
   大きく下がったが、両者の比率(=torch.compileによる倍率)は2.70x→2.77xと
   ほぼ変化しなかった。バッチ化は「1回のPython/カーネル呼び出しで処理する
   軌道数を増やしてオーバーヘッドを償却する」高速化であり、torch.compileは
   「1回の呼び出し内のPythonループのオーバーヘッドを削減する」高速化である。
   両方とも「固定オーバーヘッド対計算本体の比率を下げる」という同じ効き方を
   するため、片方を強化してももう片方の効果を大きくは変えない。真の計算量
   (RNEAの反復回数)自体を減らさない限り、これ以上の大幅な高速化は望めない。

10. **RNEAの反復計算自体を軽量NNで置き換えると大幅に高速化できるが、同じ学習
    レシピ(データ量・エポック数)ではRNEAベース版に比べ精度が大きく劣化する**
    (#19): 質量行列M(q)・バイアス力bias(q,q_dot)をそれぞれ小さなMLPで直接
    近似する`LightweightGrayBoxModel`を実装した(摩擦の構造化はそのまま維持、
    M(q)はコレスキー分解で対称正定値性を保証)。速度はtorch.compileなしでも
    真値シミュレータの約12-13倍(バッチ50本×200ステップで7.68秒→0.57秒)。
    しかし`StructuredFrictionGrayBoxModel`(摩擦係数12個のみ学習)と全く同じ
    学習レシピ(150軌道、K_MAX=10まで105エポック)で学習したところ、検証損失は
    RNEA版の0.0016に対し0.038(約24倍悪化)、開ループRMSEは0.2秒間で0.4-0.9
    (RNEA版)に対し4.6-6.3、PTP制御の最終誤差は0.06(RNEA版)に対し3.3
    (しきい値0.2を大きく超え失敗)だった。RNEAベースのグレーボックスは既知の
    物理構造という強い帰納バイアスにより少ないデータでも汎化するが、MLPは
    その帰納バイアスを持たないためデータ・学習量への要求が大きく異なる。
    「アーキテクチャを変えれば速くなる」ことは確認できたが、同じ学習コストで
    同等の精度を得るには追加のデータ・正則化・学習時間が必要(未着手)。

11. **「真値シミュレータに対する倍率」と「実時間比」は別の指標であり、用途に
    よってどちらが重要かが変わる**(#22): #16で確認した「真値シミュレータの
    2.5倍高速」はバッチ50本を並列実行した場合の倍率であり、そのまま「実時間より
    速く動く」ことを意味しない。実際に単一軌道(バッチ化なし、1台のロボットを
    その場で制御する想定)で実時間(dt=0.002sの積み重ね)と比較したところ、
    torch.compile込みでも実時間の約0.18倍(≒実時間の5.4倍の計算時間がかかる、
    リアルタイムより遅い)だった。一方、バッチ処理(50シナリオ並列)では
    1軌道あたり換算で実時間の約6.5倍(実時間より速い)。バッチ化によって
    得られる高速化は「並列に多数のシナリオを回す用途(強化学習・大量
    シミュレーション)」でのみ実時間を上回り、「1台をリアルタイム制御する」
    用途では現状のRNEAベース設計のままでは実時間に届いていない。

12. **学習パラメータを持たない計算(既知の物理)は、推論時にPyTorchの外に
    出して専用の高速な実装に置き換えられる**(#26): #22で「単一軌道の
    リアルタイム制御はtorch.compileでも実時間に届かない」ことが分かった。
    グレーボックスの質量行列M(q)・バイアス力bias(q,q̇)は摩擦係数と違い
    学習パラメータを一切持たない(既知の物理をそのまま計算しているだけ)ため、
    学習後の推論・制御時は自動微分が不要になり、PyTorchである必要が原理的に
    ない。numbaで単一状態向けにJITコンパイルした実装に置き換えたところ、
    numpyの約45倍・torch.compile単一軌道版の約17倍高速化し、計算トルク法
    PTP制御の閉ループ全体(コントローラ+プラント)でも実時間の約1.8倍
    (実時間より速い)を達成した(真値モデルと数値誤差の範囲で一致)。
    ただし学習(勾配計算)には使えず(numbaは自動微分をサポートしない)、
    バッチ処理にも効果がない(各軌道が独立にJIT実行されるため#18のバッチ
    化のような償却効果が働かない)。「学習には自動微分が必要な実装、推論には
    それを必要としない専用の高速実装」を使い分けるという設計が有効だった。

13. **多段ロールアウト損失は、M(q)・bias(q,q̇)のような「関数そのもの」を
    学習する信号としては弱く、既知の物理を使って直接教師あり回帰できる
    なら、そちらの方がはるかに強い学習信号になる**(#32): #24(容量増)・
    #30(データ4倍)のいずれでも軽量NNの精度が伸びなかったため、真の
    `mass_matrix(q)`/`bias_forces(q,q̇)`をロールアウトなしで直接MSE回帰
    してみたところ、M(q)は相対誤差2.4%まで学習できた。これは同じ
    アーキテクチャ・データ量でロールアウト損失から間接的に学習した場合
    より明らかに良く、「MLP自体の表現力が足りない」のではなく「ロールアウト
    損失という学習信号が間接的すぎる」ことが#19-#30の精度不足の一因
    だったと分かった。一方でbias(q,q̇)は同じ直接回帰でも相対誤差17.5%で
    頭打ちになり、コリオリ項・重力項の結合はM(q)よりMLPにとって本質的に
    学習しづらい関数であることも分かった。学習済みM(q)/bias(q,q̇)を凍結し
    摩擦だけをロールアウト損失で学習する2段階カリキュラムに切り替えると、
    学習損失自体は改善しなかった(bias(q,q̇)の残差誤差を摩擦(12スカラー、
    速度のみに依存)では吸収しきれないため)が、PTP制御の実用精度は
    #19/#30よりはるかに改善し、q6の巻き付き・暴走という質的な失敗も
    解消した。「学習損失の大小」と「実用上の精度・安定性」は必ずしも
    同じ方向に動かないことを重ねて確認した(#30の教訓と対応)。

14. **多出力回帰で成分間の振幅差が大きいとき、正規化なしのMSEは大振幅
    成分に支配され小振幅成分の勾配がほぼ消えるが、正規化しても「全成分を
    均等に扱う」ことと「小さなモデルで全成分を同時に高精度化できる」ことは
    別問題である**(#32): #32のbias_net直接教師あり回帰で、正規化なしの
    生MSEでは腕関節(振幅6.6-13.3)が損失を支配し手首関節(振幅0.02-1.0)の
    相対誤差がほぼ100%(ゼロ予測と同水準)になっていた。Phase2-M8の教訓
    通り成分ごとの標準偏差で正規化すると手首関節は大きく改善したが、
    今度は元々良かった腕関節(特にq1)の精度が23%→76%まで悪化する
    トレードオフが生じた。原因は、mass_net/bias_netが6出力を1つの
    小さな隠れ層(hidden_dim=64)で共有しているため、全成分を均等な重みで
    同時に高精度化するだけの表現力がなく、正規化の有無によって「どの成分を
    犠牲にするか」が変わるだけだったこと。また質量行列M(q)では逆に、
    分散が極端に小さい(ほぼ定数の)成分を標準偏差で正規化すると、些細な
    絶対誤差が正規化後に爆発し学習全体を不安定化させることも確認した
    (M(q)は生MSEのまま据え置いた)。「正規化すれば多出力の不均衡が
    解決する」と単純に考えず、(a) 振幅差の原因が真に無視できない物理量の
    差なのか、(b) 正規化後に数値的に安定か、(c) モデル容量が全成分を
    同時に満たせるだけあるか、を個別に確認する必要がある。

## 使い方

```
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pytest tests/                       # 全テスト実行

python verify_physics.py            # M1: 真値シミュレータのエネルギー保存則を検証
python -m src.train                 # M2: グレーボックスサロゲートを学習(outputs/model_graybox.ptに保存)
python -m src.evaluate_graybox      # M2: 開ループロールアウト誤差・摩擦係数の検証
python -m src.evaluate_ptp          # M2: 計算トルク法PTP制御(真値/サロゲート比較)
python -m src.evaluate_ptp_scenarios  # M2: 多数のランダムシナリオでのPTP制御検証
python -m src.evaluate_ptp_scenarios_numba  # 同上をnumba版(単一軌道向け)で検証
python -m src.benchmark_speed       # 真値シミュレータ/サロゲートの計算速度比較
```

## 主要ファイル

- `src/physics.py`: 真値シミュレータ(修正DH+RNEA、numpy)
- `src/model.py`: グレーボックスサロゲート(RNEAのtorch版+構造化摩擦、学習用)
- `src/physics_numba.py`: RNEA・PTP閉ループのnumba版(単一軌道の高速推論・制御用)
- `src/dataset.py`: 学習・評価用の軌道データセット生成
- `src/train.py`: 学習スクリプト(マルチステップ損失+カリキュラム学習)
- `src/control.py`: 計算トルク法PTPコントローラ
- `src/evaluate_graybox.py` / `src/evaluate_ptp.py`: 検証スクリプト
- `verify_physics.py`: M1のエネルギー保存則検証スクリプト(リポジトリ直下)
